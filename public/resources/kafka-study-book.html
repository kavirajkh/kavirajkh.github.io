1 · Architecture and why Kafka is fast

Kafka is a distributed, partitioned, replicated commit log. Speed comes from doing less: append-only writes, OS page cache, zero-copy, batching.

⚡ At a glance
  • What: Brokers host topic partitions; each partition is an append-only log with one leader and followers.
  • Must-know: ★ sequential I/O, page cache, zero-copy, batching, pull-based consumers.
  • Must-know: ★ partition is the unit of parallelism, ordering and replication.
  • Pitfall: saying Kafka is fast because it is in-memory; it is disk-based and leans on the page cache (TLS defeats zero-copy).
  • Versions: 0.8 replication; 0.9 new consumer; 4.0 ZooKeeper removed.
BrokerA server storing partition logs and serving produce/fetch. A cluster has N brokers; one acts as controller.
Topic / PartitionTopic = named stream. Partition = ordered, immutable, append-only log; the unit of parallelism and ordering.
Producer / ConsumerProducers append to partition leaders; consumers pull from leaders (or follower replicas, 2.4+), tracking offsets.
ControllerElects partition leaders, tracks broker liveness. ZooKeeper-based until 3.x; KRaft quorum from 3.3, only option in 4.0.
Consumer groupSet of consumers sharing a group.id; each partition goes to exactly one member, so scale-out = more consumers up to #partitions.

Worksheet

In two minutes, explain what Kafka is and how it differs from a traditional message queue.
Answer

Kafka is a distributed, partitioned, replicated, append-only commit log. Messages are not deleted on consumption; they are retained by time/size (or compacted) and each consumer group tracks its own offset. Multiple groups can read the same data independently and can replay.

Traditional queues (RabbitMQ, SQS standard) push/lease a message to one consumer and delete it on ack; ordering and replay are limited. Kafka trades per-message routing/ack flexibility for throughput, ordering per partition and replayability. Queue-like semantics are arriving via share groups (KIP-932, early access in 4.0, preview in 4.1, verify).

Why is Kafka fast even though it writes to disk?
Answer

(1) Sequential append-only I/O; (2) writes go to the OS page cache and are flushed asynchronously (durability comes from replication, not fsync per message); (3) consumers reading near the tail are served from page cache; (4) zero-copy sendfile from page cache to NIC; (5) batching and end-to-end compression; (6) partitioning spreads work.

Failure mode: a consumer that lags far behind reads cold segments from disk, evicting hot pages and slowing everyone ("cache pollution"). Tiered storage (KIP-405) mitigates by serving old data from remote storage.

Kafka does not fsync each message by default. Is that a durability bug? How is data protected from a broker crash?
Answer

Durability comes from replication: with acks=all and min.insync.replicas=2 on RF=3, a write is acknowledged only after at least 2 replicas have it in memory (page cache). A single broker crash loses nothing because another in-sync replica has it. Simultaneous power loss of all replicas could lose unflushed data.

You can force flush.messages=1/flush.ms, but it destroys throughput and is rarely worth it; instead spread replicas across racks/AZs (broker.rack). A restarted broker truncates its log to the high watermark/leader epoch checkpoint and re-fetches from the leader, so unflushed tails are recovered from peers.

What is the role of the page cache, and how would you size broker RAM?
Answer

Kafka keeps little in the JVM heap (typically 4-6 GB is plenty); the rest of RAM becomes page cache. Aim for enough cache to hold the "hot window" that consumers read: roughly write throughput x (acceptable consumer lag in seconds). Example: 100 MB/s ingest and consumers lagging up to 60 s means about 6 GB of hot data per broker (divide by broker count and multiply by RF).

Do not give the JVM 64 GB heap: long GC pauses and less page cache. G1 with a small heap is the norm.

A teammate says "just enable TLS everywhere, it is only a small overhead". What would you check for Kafka specifically?
Answer

TLS removes zero-copy for consumer fetches, adds CPU for encrypt/decrypt on brokers and clients, and increases latency on connection setup. Check: broker CPU headroom (benchmark with kafka-producer-perf-test.sh --producer-props security.protocol=SSL ...), whether JDK uses hardware AES (AES-NI) and TLS 1.3, connection pooling (long-lived connections), and whether inter-broker traffic is also encrypted (security.inter.broker.protocol). The trade-off is almost always worth it for PII/payroll data; the fix is capacity, not plaintext.

Worksheet

What is an offset? Is it unique across a topic?
Answer

An offset is the sequential position of a record inside one partition. It is unique only within that partition; uniqueness across a topic requires (topic, partition, offset). Consumers store the next offset to read (last processed + 1) per partition in __consumer_offsets. Ordering is guaranteed only within a partition.

What is a segment and how does retention interact with it?
Answer

A partition log is split into segment files named by base offset. Only the active segment is written. A segment rolls when it reaches segment.bytes (1 GiB) or is older than segment.ms (7 days) (or the index is full). Retention (retention.ms, 7 days default; retention.bytes) deletes whole closed segments whose newest record is older than the limit.

Consequence: data may live longer than retention.ms if the segment is still active or its newest record is recent. A low-volume topic with 1 GiB segments will keep data far longer than 7 days; set segment.ms smaller (for example 1 day) if you need timely deletion (GDPR, for instance).

How do you consume from the position corresponding to "yesterday 9 AM"?
Answer

Use the time index: consumer.offsetsForTimes(Map<TopicPartition,Long>) returns the earliest offset whose timestamp is >= given time, then seek().

Caveat: with CreateTime timestamps the index assumes mostly monotonic timestamps; badly skewed producer clocks give surprising results. Returns null if no record is newer.

You increased a topic from 6 to 12 partitions and downstream consumers started seeing events for the same employee out of order. Why, and how do you migrate safely?
Answer

The default partitioner uses murmur2(key) % numPartitions. Changing n remaps keys: new events for E42 may go to partition 9 while older unprocessed events remain in partition 3, consumed by a different thread/instance, so ordering is lost during the transition.

Safe approaches: (a) over-provision from the start (for example 3x expected need) so you never resize; (b) create a new topic with the target count, dual-publish or mirror, drain the old topic to its end (consumers reach the end offset), then switch consumers; (c) if resize is unavoidable, pause producers, wait for consumers to drain (lag 0), alter partitions, resume. Compacted topics are even worse: older values for a key may exist in the old partition.

Explain the on-disk layout of a partition and how a consumer fetch for offset 70000 is served efficiently.
Answer

Directory topic-partition/ holds segment triples named by base offset: .log, .index (sparse offset to file position, one entry per ~index.interval.bytes = 4 KiB), .timeindex. The broker binary-searches the segment list (in-memory skip-list by base offset) for the segment with the largest base offset <= 70000, binary-searches its mmap'd sparse index for the nearest lower entry, then scans the .log sequentially to the exact record. The response is sent via zero-copy (no TLS). Everything after the first lookup is sequential I/O, usually from page cache.

Worksheet

Explain acks=0, 1 and all. Which one do you use for payroll events and with what companion settings?
Answer

acks=0: no wait, possible silent loss. acks=1: leader appended but not replicated; a leader crash right after ack loses data. acks=all: leader waits for all in-sync replicas.

For payroll: acks=all + topic min.insync.replicas=2 + RF=3 + enable.idempotence=true + unclean.leader.election.enable=false. Note acks=all alone with min.insync.replicas=1 degrades to leader-only when followers fall out of ISR, which is the classic mistake.

How does the idempotent producer work and what does it NOT guarantee?
Answer

On init the broker assigns a producer id (PID) and epoch. Each batch carries a per-partition sequence number. The broker keeps the last 5 batches' sequences per PID/partition; a duplicate sequence is acknowledged but not appended; an out-of-order sequence gives OutOfOrderSequenceException.

Guarantees: no duplicates and no reordering from retries within one producer instance's session, per partition. Not guaranteed: dedup across producer restarts (a new instance gets a new PID unless transactional.id is used), across partitions atomically, or an application-level duplicate you create by calling send twice. For cross-session/atomic guarantees use transactions.

What do linger.ms and batch.size do, and how do you tune for throughput vs latency?
Answer

A batch is sent when it reaches batch.size bytes or linger.ms has elapsed since the first record. Throughput tuning: linger.ms=10-50, batch.size=64-256 KB, compression.type=lz4 or zstd, larger buffer.memory. Latency tuning: linger.ms=0-1, keep batches small, acks=1 only if loss is acceptable (usually not).

Measure with kafka-producer-perf-test.sh --topic t --num-records 5000000 --record-size 1024 --throughput -1 --producer-props bootstrap.servers=b1:9092 linger.ms=20 batch.size=131072 compression.type=lz4 and watch metrics batch-size-avg, records-per-request-avg, request-latency-avg.

Explain delivery.timeout.ms, request.timeout.ms, retries and max.block.ms. What happens when the broker is unreachable for 3 minutes?
Answer

request.timeout.ms (30 s) = wait for one request's response. delivery.timeout.ms (120 s) = total time budget from send() returning to success/failure, covering batching, retries and backoff (retry.backoff.ms 100 ms, with max backoff since 3.7). retries is effectively infinite; the time bound is what matters (must be >= linger.ms + request.timeout.ms). max.block.ms (60 s) bounds how long send() blocks on a full buffer or missing metadata.

3 minutes outage: queued batches expire after 120 s; callbacks get TimeoutException; meanwhile buffer fills (32 MB) and send() starts blocking up to 60 s then throws. You need an application policy: fail the request, spill to a local outbox table, or retry from a DB. This is exactly why the outbox pattern exists (section 14).

With max.in.flight.requests.per.connection=5, how can ordering still be preserved on retry?
Answer

With idempotence, each batch has a sequence number; the broker only appends the next expected sequence. If batch 2 fails and batch 3 arrives first, the broker rejects 3 (out of order, retriable), the client re-sends 2 then 3 in order. The broker tracks the last 5 batches, hence the cap of 5. Without idempotence you must set max.in.flight=1 to keep order, at big throughput cost.

A producer sends records with null keys. How are they distributed? What changed in 2.4/3.3?
Answer

Old (pre-2.4): round-robin per record, creating many tiny batches. Sticky partitioner (KIP-480, 2.4) sticks to one partition until a batch is full or sent, then switches. Uniform sticky (KIP-794, 3.3) additionally adapts so slow brokers get fewer records. Result: bigger batches, lower latency and CPU. Null-key records have no ordering expectations; for ordering always set a key.

How would you serialize event payloads, and where does a schema id go? Compare JSON, Avro, Protobuf.
Answer

Options: StringSerializer + JSON (simple, no contract enforcement, large); Avro/Protobuf/JSON Schema via Schema Registry serializers (KafkaAvroSerializer etc.) writing a magic byte + 4-byte schema id + payload, enabling compatibility checks (section 12). Protobuf: compact, field numbers give easy evolution, strong cross-language support. Avro: compact, needs the writer schema at read time (from registry), rich evolution rules with defaults.

Put cross-cutting metadata (eventId, eventType, traceId, schema version, tenant) in headers (0.11+) so routing and tracing do not require deserialising the body.

Worksheet

How does a consumer group scale and what is the limit?
Answer

Partitions are divided among group members; each partition has at most one consumer in the group at a time. Throughput scales by adding consumers up to the partition count; beyond that, extra consumers are idle. To scale further you must add partitions (with the ordering caveat) or hand work to a thread pool after poll (losing simple offset semantics). Different groups consume independently, each with its own offsets.

Difference between session.timeout.ms, heartbeat.interval.ms and max.poll.interval.ms?
Answer

Heartbeats are sent by a background thread every heartbeat.interval.ms (3 s); if the coordinator hears none for session.timeout.ms (45 s since 3.0) the member is removed (crash/network detection). max.poll.interval.ms (5 min) is the maximum time between two poll() calls; exceeding it makes the client leave the group proactively (a stuck handler), and the next commit fails with CommitFailedException. Rule of thumb: heartbeat = session/3; processing time per poll batch < max.poll.interval / 2.

What happens when a consumer joins a group with no committed offset and auto.offset.reset=latest vs earliest?
Answer

latest: starts at the end, misses everything produced before the first poll assignment (messages produced while the group was starting are lost to it). earliest: starts at the beginning of retained data, processing the entire backlog. none: throws NoOffsetForPartitionException. This also applies when a committed offset is out of range (retention deleted it): a long-paused group with latest silently skips data; with earliest it reprocesses everything retained. Note committed offsets expire after offsets.retention.minutes (7 days, since 2.0) once the group is empty.

Describe the poll loop contract and why you should not do blocking work between polls.
Answer

poll() does group membership, fetch, offset commit (auto) and rebalance callbacks all on the calling thread. KafkaConsumer is not thread-safe (only wakeup() may be called from another thread). Blocking too long causes eviction (max.poll.interval.ms), a rebalance, and duplicates. Patterns for slow work: reduce max.poll.records; or hand records to a worker pool, pause() the partitions, keep calling poll() (heartbeats continue), and commit only offsets of completed contiguous records on the polling thread, then resume().

How can consumers read from a follower in the same rack (KIP-392) and why would you?
Answer

Set broker replica.selector.class=org.apache.kafka.common.replica.RackAwareReplicaSelector with broker.rack set, and consumer client.rack=us-east-1a. The leader tells the consumer to fetch from a same-rack replica. Benefit: avoids cross-AZ data transfer charges and latency (on AWS cross-AZ traffic is billed). Trade-off: data visibility is limited by the high watermark as propagated to the follower, so end-to-end latency can be slightly higher.

Worksheet

What triggers a consumer group rebalance?
Answer

A member joins or leaves (graceful close or crash detected by session timeout), a member exceeds max.poll.interval.ms, the subscribed topic set changes (including regex-matched new topics), partitions of a subscribed topic are added, or the coordinator moves (broker failure). During an eager rebalance consumption stops across the group.

What is incremental cooperative rebalancing and how do you enable it?
Answer

KIP-429: instead of revoking everything, the leader computes the new assignment and members revoke only the partitions that must move (round 1), then rejoin and receive the moved partitions (round 2). Unaffected partitions continue processing. Enable with partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor (default list since 3.0 is Range then CooperativeSticky, so groups still start eager until Range is dropped). Migrating from an eager assignor requires a two-phase rolling restart so mixed members agree on a common protocol. Kafka Connect uses its own incremental protocol (KIP-415, 2.3); Streams adopted cooperative in 2.4.

How does static membership (KIP-345) reduce rebalances, and what is the trade-off?
Answer

With group.instance.id the broker remembers the member's assignment. If the instance restarts and rejoins with the same id within session.timeout.ms, it gets the same partitions back and no rebalance occurs. Rolling deployments become quiet. Trade-off: a truly dead instance's partitions sit unprocessed until the (larger) session timeout expires, so you raise session.timeout.ms (for example 60-120 s) and accept slower failure detection. Duplicate group.instance.id values fence the older client with FencedInstanceIdException.

What problem does KIP-848 solve and what changes for operators?
Answer

The classic protocol relies on a client-side group leader and a global synchronisation barrier (JoinGroup/SyncGroup) so any change stops all members. KIP-848 (GA in 4.0, early access 3.7, verify) moves assignment to the broker-side group coordinator (group.protocol=consumer on clients), uses a continuous heartbeat RPC (ConsumerGroupHeartbeat), reconciles each member independently (only affected members pause), and removes client-driven assignors (server assignors like uniform/range; custom server-side possible). Operators: session/heartbeat intervals become broker/group configs (group.consumer.session.timeout.ms, group.consumer.heartbeat.interval.ms), you need brokers on 4.x (or 3.7+ with the feature flag, verify) and new metrics. Large groups (hundreds of members) see much smaller pauses.

Lag keeps growing and the group rebalances every few minutes. Walk through diagnosing it.
Answer

1) kafka-consumer-groups.sh --describe --group g shows lag per partition and member; --state shows whether it is Stable/PreparingRebalance. 2) Check client logs for "Member ... sending LeaveGroup request ... consumer poll timeout has expired" which means max.poll.interval exceeded: handler too slow or too many records per poll. 3) Look at GC logs and downstream latency (DB, HTTP calls) for pauses. 4) If rebalances align with deploys/autoscaling use static membership and cooperative assignor. 5) Remedies: lower max.poll.records, raise max.poll.interval.ms only if processing is legitimately long, move slow work off the poll thread with pause/resume, add timeouts to downstream calls, then add partitions/consumers for capacity. The loop (evict, rebalance, reprocess uncommitted records, evict again) is why lag grows even though CPU looks fine.

Worksheet

When do you commit offsets, and what delivery guarantee does each choice give?
Answer

Commit after processing gives at-least-once (crash between process and commit causes duplicates). Commit before processing gives at-most-once (crash loses records). Auto-commit is effectively "commit at next poll", which can commit unprocessed records if your handler is async or fail to commit processed ones, so it is at-least-once only if processing is synchronous and finishes before the next poll. Exactly-once requires either a Kafka transaction (Kafka sink) or an idempotent/transactional external sink.

commitSync vs commitAsync: which do you use and why?
Answer

commitSync blocks and retries on retriable errors; simple and safe but adds latency per batch. commitAsync does not retry (a later commit may already have succeeded, retrying an older one would move the offset backwards). Common pattern: commitAsync inside the loop, and a final commitSync in finally/on revoke/close. In Spring, AckMode.BATCH (default) commits after each poll batch; MANUAL_IMMEDIATE with Acknowledgment.acknowledge() for control.

You need to reprocess the last 7 days of events for one consumer group. How?
Answer

Check retention covers 7 days (retention.ms >= 604800000; otherwise data is gone, or use tiered storage). Stop the group (scale to 0), then kafka-consumer-groups.sh ... --reset-offsets --to-datetime <now-7d> --execute; or use a separate new group id with auto.offset.reset=earliest (leaves the live group untouched, safer). Ensure idempotent handlers and downstream side effects (emails, payments) are suppressed or deduplicated for replay mode. Throttle with max.poll.records so downstream systems are not flooded; monitor lag falling.

What is CommitFailedException and how do you handle it?
Answer

Thrown when a commit is attempted by a member that is no longer part of the generation (rebalance happened after exceeding max.poll.interval or session timeout). The records of the batch will be redelivered to whoever now owns the partition, so handlers must be idempotent. Fix root cause (slow processing), not the exception: smaller batches, pause/resume, timeouts. In a rebalance listener, onPartitionsLost means do not commit.

Design a consumer that processes records in parallel threads but still commits correct offsets.
Answer

Per-partition ordering must hold, so parallelise across partitions (or keys), not within a partition. Option: one consumer thread polls; each partition's records go to a per-partition (or per-key-hash) single-thread executor; the poll thread tracks, per partition, the highest offset such that all lower offsets are completed (a contiguous watermark, tracked with a TreeSet/bitset) and commits watermark+1; use pause/resume for back-pressure when queues exceed a bound; on revoke, wait for in-flight tasks and commit before releasing. Libraries: Confluent Parallel Consumer implements this (key-level parallelism). Failure mode: committing max offset instead of contiguous watermark loses records on crash.

Worksheet

Explain at-most-once, at-least-once and exactly-once in Kafka. Which is the default practical choice?
Answer

At-most-once: may lose, never duplicates. At-least-once: never loses, may duplicate (default practical choice: acks=all, commit after processing). Exactly-once: each input affects output once, achieved inside Kafka with transactions. For anything touching an external system, practical design is at-least-once delivery + idempotent processing = "effectively once".

How do Kafka transactions work at a high level?
Answer

Each producer has a transactional.id mapped to a PID + epoch in the transaction coordinator (__transaction_state). Within begin/commit, records are written normally but flagged transactional; the coordinator tracks partitions involved. sendOffsetsToTransaction includes consumer offsets. On commit the coordinator does a two-phase commit: writes PREPARE_COMMIT to its log, then writes COMMIT control markers to every involved partition; read_committed consumers use the LSO and an aborted-transaction index to skip aborted data. A new instance with the same transactional.id bumps the epoch, fencing zombies.

What is zombie fencing and what did KIP-447 change?
Answer

If an instance hangs (GC, partition) while its partitions are rebalanced to another instance, the old "zombie" might still commit. Fencing: the new owner calls initTransactions() with the same transactional.id, bumping the epoch; the broker rejects the zombie with ProducerFencedException. Before 2.5 you needed one transactional producer per input partition with transactional.id derived from topic-partition. KIP-447 (2.5) lets one producer serve many partitions: sendOffsetsToTransaction(offsets, consumer.groupMetadata()) uses the group generation for fencing. Streams exactly_once_v2 (2.6 / 3.0 naming) builds on it.

Can Kafka give exactly-once into a database? Design it.
Answer

Not by itself. Options: (1) Idempotent consumer: upsert keyed by a unique eventId/business key (INSERT ... ON CONFLICT DO NOTHING), or a processed_events(event_id PRIMARY KEY) table written in the same DB transaction as the business change. (2) Store offsets in the DB in the same transaction as the data and on startup seek() to those offsets (disable Kafka commits). (3) Use Kafka Connect JDBC sink with insert.mode=upsert and pk.mode=record_key. Pick (1) for simplicity: at-least-once delivery plus a unique constraint gives effectively-once.

A transaction hung for 10 minutes and downstream read_committed consumers stopped. What happened and how do you prevent it?
Answer

An open transaction pins the Last Stable Offset: read_committed consumers cannot pass it until the transaction is committed, aborted or times out (transaction.timeout.ms set by the producer, capped by the broker transaction.max.timeout.ms=15 min). A producer that crashed mid-transaction leaves it open until the coordinator times it out. Prevention: small, short transactions, a sensible transaction.timeout.ms (for example 10-30 s), no external calls inside the transaction, alert on LSO lag (metric: consumer lag measured against LSO) and use kafka-transactions.sh find-hanging / abort (3.x tooling, verify) for manual cleanup.

Which consumer setting must accompany transactional producers, and what is its default?
Answer

isolation.level=read_committed; the default is read_uncommitted, which exposes aborted and in-flight transactional records. Also disable auto commit for consume-transform-produce loops and commit via sendOffsetsToTransaction.

How do you guarantee ordering of events for one employee in Kafka?
Answer

Use the employeeId as the record key so the default partitioner sends all of that employee's events to the same partition; a partition is an ordered log and one consumer per group reads it. Additionally on the producer: idempotence (max.in.flight<=5) so retries do not reorder. Do not change the partition count afterward. Across employees there is no ordering guarantee, which is fine.

You have a hot key causing one partition to lag. Options?
Answer

First confirm: per-partition bytes in/out and lag (kafka-log-dirs.sh, metrics by partition). Options: (1) key salting key + "#" + (hash(eventId) % N) if consumers only need ordering per (key, salt) or can re-merge; (2) change the key to a finer-grained entity (orderId rather than tenantId); (3) custom partitioner giving the hot key a dedicated set of partitions; (4) split big tenant to its own topic and consumer group; (5) raise consumer capacity with key-parallel processing within the partition (Parallel Consumer) while keeping per-key order. Trade-off: every spreading technique relaxes the ordering scope; document what ordering consumers can rely on.

How many partitions should a new topic get? How do you reason about it?
Answer

Start from required throughput divided by the measured per-partition throughput (producer and consumer side, take the larger partition count), then consider max desired consumer parallelism and growth for 1-2 years (because partitions cannot be reduced and increasing breaks key mapping). Check broker limits: total partition replicas per broker, file handles, replication fetch threads. Typical moderate topic: 6-24 partitions; high-volume: 50-200+. Over-partitioning costs open files, memory and recovery time; under-partitioning caps scalability.

Events for the same entity arrive out of order at a consumer even with a keyed topic. List causes.
Answer

(1) Producer retries without idempotence and max.in.flight>1. (2) Partition count change remapped the key. (3) Different producers (services) for the same entity each with its own clock/network path: Kafka orders by arrival, not event time. (4) Producer sends to different topics (event type per topic): no cross-topic order. (5) Consumer-side thread pool reorders processing. (6) Replays/DLT retries re-inject older events later. Mitigations: single topic per entity type with key, version/sequence numbers on events with consumer-side "ignore if older version" check, event-time based reconciliation.

Why might you intentionally use a single topic for several event types of one aggregate?
Answer

Ordering exists only within a partition of one topic. Hired, SalaryChanged, Terminated for E42 must be applied in order, so publish them to the same topic keyed by employeeId (event type in a header or schema union / Schema Registry subject name strategy RecordNameStrategy or TopicRecordNameStrategy). Separate topics per event type would let a consumer see Terminated before Hired.

Worksheet

What is the ISR and what happens when a follower falls behind?
Answer

The ISR is the set of replicas (including the leader) considered caught up. If a follower has not fetched up to the leader's log end within replica.lag.time.max.ms (30 s), the leader removes it from the ISR (ISR shrink; visible as under-replicated partitions). It rejoins (ISR expand) once it catches up. Only ISR members can be elected leader (unless unclean election). With acks=all the write needs acks from all current ISR members, and the ISR must still be >= min.insync.replicas.

Explain acks=all together with min.insync.replicas. What exception do producers see when ISR is too small?
Answer

acks=all means all in-sync replicas must acknowledge; min.insync.replicas sets the floor on how many that is. If ISR < min.isr the broker rejects with NotEnoughReplicasException (before write) or NotEnoughReplicasAfterAppendException (after append, retriable). Producers retry within delivery.timeout.ms, then fail. This turns "silent under-replication" into a loud availability problem, which is the right trade-off for payroll data.

What is the high watermark and why was the leader epoch introduced (KIP-101)?
Answer

HW = offset below which data is replicated to all ISR; consumers can read only to HW. Followers learn HW from the leader's fetch responses with a delay. Before KIP-101 a follower that restarted truncated to its own last known HW, which could be stale; with unlucky leader changes, logs could diverge or acknowledged data be lost (the "HW truncation" scenario with acks=all and replicas restarting back-to-back). The leader epoch (term number stored per message batch and in a checkpoint file) lets a follower ask the new leader "what is the end offset of epoch N?" (OffsetsForLeaderEpoch) and truncate precisely to the divergence point.

When would you enable unclean leader election?
Answer

When availability is worth more than possibly losing/diverging committed data: metrics, logs, clickstream where a gap is tolerable. It lets an out-of-sync replica become leader when the entire ISR is down, so the partition becomes available quickly but records that only existed on the dead replicas vanish and consumers may see offsets rewind/skip. Never for payroll, financial or audit topics. Can be set per topic; default false since 0.11.

A 3-broker cluster with RF=3, min.isr=2: broker 2 dies, then broker 3 dies. What do producers and consumers experience, and how do you recover?
Answer

ISR drops to 1 (< 2): producers with acks=all get NotEnoughReplicas errors (writes rejected); consumers can still read committed data (below HW) from the surviving leader. No data loss. Recovery: bring brokers back; they truncate to the leader epoch boundary, fetch, rejoin ISR; producers resume. Emergency option for a stuck write-path: temporarily lower the topic's min.insync.replicas to 1 (dynamic config, kafka-configs.sh --alter) accepting the risk, then restore it. If both dead brokers' disks are gone and you enable unclean election you may lose records only they had.

What does broker.rack achieve and what is a good replica layout across 3 AZs?
Answer

When creating topics and reassigning, Kafka spreads each partition's replicas across distinct racks if possible. With RF=3 over 3 AZs each partition has one replica per AZ, so an AZ outage leaves 2 of 3 replicas (ISR still >= 2). With RF=3 over 2 AZs one AZ holds two replicas and losing it drops ISR below 2. Stretching one cluster across regions is not recommended due to latency; use MirrorMaker 2 / cluster linking across regions.

Retention vs compaction: when do you use each?
Answer

Retention (delete): keep events for a time/size window; event streams, audit trails (7 days default). Compaction: keep latest value per key indefinitely; "current state" topics (employee profile, config, changelog for KTable), allows new consumers to bootstrap complete state without a database snapshot. Combined compact,delete bounds growth. Event sourcing wanting full history uses delete with long/infinite retention (or tiered storage), not compaction.

How do you delete a record from a compacted topic, and why might it linger?
Answer

Produce a tombstone: same key, null value. Compaction removes older values for the key; the tombstone itself is retained for delete.retention.ms (24 h) then removed. It lingers if: the segment is still the active one (never compacted), the dirty ratio has not reached threshold, min.compaction.lag.ms is set, or cleaner threads are behind/dead. Downstream sinks must handle null values (JDBC sink delete.enabled=true).

What is tiered storage and what are its constraints?
Answer

KIP-405: brokers keep recent segments on local disks and offload closed segments to remote storage (S3/GCS/HDFS through a RemoteStorageManager plugin); consumers reading old data are served from remote. Benefits: decouple storage from compute, retain months/years cheaply, faster broker recovery/rebalance (less local data). Config: broker remote.log.storage.system.enable=true, topic remote.storage.enable=true, local.retention.ms, retention.ms. Constraints: early access in 3.6, production-ready 3.9 (verify), not for compacted topics, disabling per-topic has limits in older versions, and latency for cold reads is higher.

Compare event retention strategies for a payroll audit topic that must be kept 7 years.
Answer

Do not rely on a Kafka topic as the sole system of record for 7 years unless operationally mature: choose (a) Kafka with retention.ms=-1 + tiered storage (cheap) + RF=3 + backups via Connect S3 sink; or (b) Kafka for 7-30 days and archive to object storage (S3 sink connector, Parquet/Avro, partition by date) with immutability (object lock) and queryability (Athena). Include schema in archived data (Avro container files), encrypt at rest, document replay procedure. For legal deletion needs, per-subject encryption keys (crypto shredding) beat deleting from immutable logs.

A topic with retention.ms=1 day still holds 3-day-old data. Why?
Answer

Retention deletes whole closed segments only. If volume is low, the segment (up to 1 GiB or 7 days: segment.bytes/segment.ms) has not rolled, so the active segment is retained regardless. Also the deletion check runs every log.retention.check.interval.ms (5 min) and uses the newest record timestamp in the segment, which can be skewed by producer-supplied timestamps. Fix: set segment.ms to something small (for example 1 hour) for that topic.

Why use a Schema Registry instead of plain JSON?
Answer

Central, versioned contracts; compact payloads (id instead of embedding schema); automatic compatibility enforcement at registration, so incompatible producer changes fail in CI instead of breaking consumers at 3 AM; code generation; schema discovery. Explain BACKWARD vs FORWARD vs FULL compatibility with an example change.
Answer

Adding field currency with a default: BACKWARD compatible (new consumers read old messages using the default) and FORWARD compatible (old consumers ignore the unknown field) so FULL. Adding a field without default: not backward compatible (new reader cannot fill the missing field) but forward compatible. Removing a field with no default: backward compatible, not forward (old readers expect it). Rule: add/remove only optional fields with defaults and you are FULL. Upgrade order: BACKWARD means upgrade consumers first; FORWARD means producers first.

You need to rename a field or change its type in a topic with 30 days of history. How?
Answer

Avro: rename with aliases in the reader schema (backward compatible); type promotion allowed: int to long, float, double; string to bytes. Other changes are breaking. Strategy: expand-contract. Add the new field (with default) and populate both; migrate consumers; later stop writing and remove old field once old data aged out (use TRANSITIVE compatibility if old versions still exist in retention). If truly breaking: new topic/version (hr.employee.events.v2) with a translator job (Streams/Connect) and dual publish during the migration, then retire v1.

How does a consumer fail when the Schema Registry is down, and how do you make it resilient?
Answer

Deserialiser caches schema id to schema in memory, so steady-state consumption continues for already-seen ids; unseen ids (a new schema version) fail with a SerializationException until the registry returns. Producers: auto.register.schemas=true needs the registry at first send per schema; with pre-registered schemas a lookup is still needed once. Resilience: multi-instance registry behind a load balancer, primary/secondary in different AZs, client retries, and wrapping deserialisation in ErrorHandlingDeserializer so one failure goes to DLT rather than blocking the partition (section 16).

KStream vs KTable vs GlobalKTable?
Answer

KStream: every record is an independent event (append). GlobalKTable: full copy of all partitions on every instance, so you can join on any field (foreign key) without co-partitioning but at the cost of memory/disk on every node. How do state stores recover after an instance dies, and what reduces recovery time?
Answer

Each store has a changelog topic (compacted). A task migrated to another instance rebuilds RocksDB by replaying the changelog from the beginning (or from the local checkpoint if state dir survived). For big state this takes minutes to hours. Reduce with num.standby.replicas=1+ (a warm copy kept updated on another instance), persistent volumes with stable state dir (StatefulSet), static membership to avoid unnecessary task movement, and since 2.6 warmup replicas / probing rebalances (KIP-441) so tasks only move once caught up. Interactive queries can read standbys since 2.5 (KIP-535).

How does Streams achieve exactly-once and what is exactly_once_v2?
Answer

Streams wraps read-process-write in a Kafka transaction per task commit interval: output records, changelog writes and input offsets commit atomically (commit.interval.ms drops to 100 ms under EOS). Results are visible to read_committed consumers only. exactly_once_v2 (KIP-732, 3.0; implementation built on KIP-447, 2.6) uses one producer per thread instead of per task, much lighter, requires brokers 2.5+. Guarantee still limited to Kafka topics: side effects in foreach/external calls can repeat.

How are late events handled in windowed aggregations?
Answer

Streams uses event time (from record timestamps / TimestampExtractor) and a per-window grace period: a record for a window is accepted until stream time passes window end + grace; later records are dropped (counted in dropped-records metric). Results emit continuously (each update) unless you apply suppress(untilWindowCloses(...)) for a single final result at the cost of latency/memory. Choose grace based on observed lateness (p99 delay), and retention of the window store >= size + grace.

Worksheet

What is the dual-write problem and how does the outbox pattern solve it?
Answer

Updating a DB and sending to Kafka are two systems without a shared transaction. If you commit then crash before sending, the event is lost; if you send then the DB commit fails, a phantom event exists. Outbox: insert the event into an outbox table in the same local DB transaction as the state change, and a separate relay (Debezium CDC or a polling publisher) publishes rows to Kafka at-least-once. Consumers must be idempotent (eventId) because the relay may re-publish after a crash.

Debezium (log-based CDC) vs a polling publisher for the outbox: trade-offs?
Answer

Log-based: near real-time, no extra queries on the DB, captures ordering in commit order and deletes, but needs DB log access (replication slot/LogMiner/binlog), extra infrastructure (Connect), careful ops. Polling: simple (a scheduled job: SELECT ... WHERE sent=false ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED), works anywhere, but adds latency and DB load, and ordering with multiple pollers needs care (partition by aggregate). Choose polling for low volume/simple, CDC for scale and latency.

How do you preserve per-aggregate ordering end to end in an outbox pipeline?
Answer

Use aggregate id as Kafka key (table.field.event.key in EventRouter). Debezium reads the log in commit order and a single connector task per table emits in that order, so events of one aggregate arrive in order within the partition. For polling publishers use one poller per shard or order by a monotonic sequence and send with the aggregate key; do not parallelise rows of the same aggregate. Include a version/sequence in the payload so consumers can detect gaps or stale replays.

A Kafka Connect sink to a database keeps failing on one malformed record. What are the options?
Answer

Set errors.tolerance=all with errors.deadletterqueue.topic.name=dlq.jdbc-sink, errors.deadletterqueue.context.headers.enable=true and errors.log.enable=true: bad records go to the DLQ with error headers while the task continues (DLQ applies to conversion/transform and sink put failures reported by the connector; not source connectors). Without it the task fails and the whole connector halts at that offset. For payroll accuracy, alert on DLQ depth > 0 and have a runbook; do not silently tolerate.

Compare Kafka Connect, a custom consumer service, and Kafka Streams for moving topic data to a database.
Answer

Connect: no code, scalable, offset management, DLQ, converters; best for standard sinks (JDBC, S3, Elasticsearch/OpenSearch). Custom consumer: full control, complex business logic and idempotent upserts, but you own the retry/DLT/lag/ops. Streams: transformations/aggregations Kafka-to-Kafka (then Connect for the last mile). Rule: Connect for plumbing, Streams for stateful computation, custom service when domain logic or non-standard sink is needed.

How does @KafkaListener concurrency relate to partitions and app instances?
Answer

Each unit of concurrency is a separate consumer thread with its own KafkaConsumer in the same group. Total consumers (instances x concurrency) beyond partition count sit idle. What is ErrorHandlingDeserializer and why do you need it?
Answer

If the underlying deserializer throws (malformed JSON, unknown Avro schema), KafkaConsumer.poll() throws repeatedly at the same offset: a poison pill that blocks the partition forever (the consumer never advances). ErrorHandlingDeserializer catches the exception, delivers a record with null value plus a header containing the failure, and the container's error handler (DefaultErrorHandler) treats it as a non-retryable deserialization failure and sends it to the DLT via DeadLetterPublishingRecoverer. Configure delegate via spring.deserializer.value.delegate.class.

Difference between ack modes RECORD, BATCH and MANUAL_IMMEDIATE?
Answer

RECORD commits after each record is processed by listener; BATCH (default) after all records from the poll are processed; MANUAL requires Acknowledgment.acknowledge() and commits at end of the batch; MANUAL_IMMEDIATE commits right away on acknowledge. With BATCH, a failure mid-batch makes the whole remaining batch redelivered (with DefaultErrorHandler seeks back to the failed record, so only unprocessed records are re-polled). Explain DefaultErrorHandler, BackOff and DeadLetterPublishingRecoverer.
Answer

When a listener throws, DefaultErrorHandler seeks the partition back to the failed record and the container re-polls it after the BackOff delay (default: 9 more attempts, no delay in older defaults; configure explicitly). After attempts are exhausted the ConsumerRecordRecoverer runs; DeadLetterPublishingRecoverer publishes the record to <topic>.DLT (same partition by default) with headers for original topic/partition/offset and exception class/message/stacktrace, then the offset is committed and consumption continues. Some exceptions are classified not-retryable (deserialization, MessageConversionException, ClassCastException, etc.) and go straight to the recoverer.

Blocking retry vs @RetryableTopic: when do you choose each?
Answer

Blocking (DefaultErrorHandler): the partition stalls while retrying, preserving order; fine for few quick retries. @RetryableTopic: failed record is published to topic-retry-0/1/... (delay implemented by pausing the retry consumer until the due time) and the main topic keeps flowing, ending in topic-dlt. Trade-offs: order is lost for that key (event 2 processed before event 1 retried), more topics/partitions to manage, delay precision bounded by poll timing. For ordered per-aggregate data with idempotent versioned events, non-blocking is fine if consumers tolerate reordering; for strict sequences prefer blocking retry or park the key.

A downstream DB is down for 30 minutes. What should your consumers do?
Answer

Retrying every record with backoff then DLT-ing thousands of good messages is wrong: the failure is not message-specific. Options: (1) classify errors; for infrastructure failures use a circuit breaker (Resilience4j) and pause the container (MessageListenerContainer.pause() via KafkaListenerEndpointRegistry), polling continues (no rebalance), resume when the health probe succeeds; (2) or set DefaultErrorHandler with unlimited/long backoff (FixedBackOff(5000, FixedBackOff.UNLIMITED_ATTEMPTS)) so the partition just waits; ensure max.poll.interval.ms exceeds the backoff or Spring's own handling (container-managed pause on seek) avoids eviction. Lag alerts will fire; after recovery the backlog drains with idempotent processing.

How do you make a listener that updates Oracle/Postgres and publishes a follow-up event safe?
Answer

Use the outbox: one DB transaction writes the state and outbox row; a relay publishes. Consumer side: idempotent via unique eventId/inbox table in the same DB transaction. If you must publish directly: the listener runs in a Kafka transaction synchronised with the DB transaction (@Transactional with DataSourceTransactionManager + container KafkaAwareTransactionManager); commit order is DB first then Kafka, so a crash between them replays the record: duplicates are possible, therefore DB write must be idempotent and the output event carries a stable eventId derived from the input (for example sha(topic,partition,offset)).

EmbeddedKafka vs Testcontainers for Kafka tests?
Answer

EmbeddedKafka (spring-kafka-test): in-JVM broker, fast startup, no Docker, good for listener/producer wiring; less faithful (version bundled with the library, no real network). Testcontainers: real broker image (apache/kafka, Confluent), can compose with Schema Registry, Debezium, Postgres and network faults (Toxiproxy); slower and needs Docker in CI. Practical split: EmbeddedKafka for most slice tests, Testcontainers for end-to-end failure and compatibility tests. Always use Awaitility rather than Thread.sleep.

What is a poison pill and how do you handle it?
Answer

A record that always fails processing (corrupt bytes, schema mismatch, bad data). Without handling, the consumer retries the same offset forever and the partition stops advancing. Handle: ErrorHandlingDeserializer for deserialization, non-retryable exception classification, bounded retries, publish to a DLT with context, commit and move on, alert and fix/replay.

How do you make a consumer idempotent?
Answer

Pick a stable unique id per event (producer-assigned UUID, or business key + version) and ensure applying it twice has the same effect: (1) natural idempotent operations (upsert by key, set-not-increment); (2) dedup table with unique constraint written in the same DB transaction; (3) version/sequence checks (WHERE version < :v); (4) for external calls pass an idempotency key (for example an HTTP Idempotency-Key header). Dedup tables need retention (purge older than the max possible redelivery window, for example topic retention plus margin).

Design DLT handling and replay for payroll outbound where 100% accuracy is required.
Answer

Failures must be visible and recoverable, never dropped. Flow: validate at ingest; permanent failures go to payroll.export.DLT with full headers; an alert fires on the first DLT record; ops triage via a small tool (read DLT, show cause, edit/skip/retry); corrected records are re-published to the original topic with the same eventId so the idempotent consumer treats them correctly; reconciliation job compares counts and totals between Kafka-produced records and what the payroll provider accepted (control totals per pay group) so silent loss is detected independently. Retention of DLT >= audit requirement. Ordering: hold subsequent events for the same employee (park key) if they depend on the failed one.

How do you handle out-of-order or late events for a state-building consumer?
Answer

Carry a monotonically increasing per-aggregate version (or event timestamp from source commit) in every event. The consumer applies only if version > stored version; equal = duplicate; gap (version > stored+1) = buffer/park or fetch from source. For eventually consistent projections use "last write wins by version". Never use consumer wall-clock time for ordering. For time-windowed analytics use event time with grace (Streams).

Explain the trade-off between at-least-once + idempotency and trying to get exactly-once everywhere.
Answer

Kafka EOS costs latency (transaction commit interval, read_committed LSO delays), throughput and operational complexity, and only covers Kafka-to-Kafka. Real systems end in a DB, HTTP call or email, where you need idempotency anyway. At-least-once with idempotent handlers is simpler, works with every sink, and survives replays, DLT re-drives and cross-cluster mirroring (which is at-least-once). Use EOS for pure stream processing (Streams aggregations, enrichment) where duplicates would corrupt counts.

Consumer lag is growing but CPU is idle on consumers. What do you check?

You observe high p99 produce latency spikes every few minutes. Likely causes?

Why does compression help even with fast disks?
Answer

Producer compresses whole batches (text/JSON/Avro often 3-5x); this cuts network I/O (client to broker, replication, fetch), disk and page cache footprint at the cost of CPU. Broker stores batches as-is if broker/topic compression.type=producer; a mismatch makes the broker recompress (CPU cost). lz4/snappy = speed, zstd = best ratio, gzip = high CPU. Larger batches compress better, so linger.ms and compression work together.

How do you measure and alert on consumer lag in a meaningful way?
Answer

Lag = log end offset - committed offset per partition. Absolute numbers mislead (10k lag on a 100 msg/s topic is 100 s; on a 10 msg/s topic is 17 minutes). Prefer lag in time (lag / consume rate) or "age of oldest unprocessed message", and detect trends and stalls (Burrow evaluates sliding windows: offset not advancing while lag > 0 = STALLED). You get paged: under-replicated partitions rising on one broker. Triage.
Answer

How do you add 3 brokers to a running cluster and rebalance?
Answer

Add brokers (new node.id), they join empty. New topics created afterwards are placed across all brokers (rack-aware). Do it in batches to avoid saturating disks; expect cold-read page cache effects.

Answer

Per user/client-id (or both) byte-rate limits for produce and fetch, and request-rate quotas, enforced by the broker by delaying responses (throttle time) not by errors. Why not stretch one Kafka cluster across two regions?
Answer

How do you secure a Kafka cluster end to end?
Answer

SASL/SCRAM vs mTLS vs OAUTHBEARER: how do you choose?
Answer

mTLS: strong, no passwords, but certificate lifecycle/rotation burden and identity is a DN; good inside a platform with automated PKI (cert-manager, service mesh-free). SCRAM: passwords hashed in the metadata store, easy for services, rotation by updating credentials, needs TLS to protect exchange. OAUTHBEARER: centralised identity/IdP, short-lived tokens, easy offboarding and claims-based principals; needs token refresh and an IdP. Kerberos: legacy enterprise. For big orgs: OAUTHBEARER/mTLS with ACLs by service principal.

How would you protect SSN or salary fields in Kafka events?
Answer

Treat Kafka as untrusted storage: encrypt sensitive fields at the producer (or gateway/outbox writer) with AES-GCM using data keys from KMS (envelope encryption: DEK per tenant/day, wrapped by KMS CMK, include key id/version), AAD bound to employeeId; only authorised consumers have KMS decrypt permission. Alternatives: tokenisation service; Confluent client-side field encryption (vendor); minimise PII by sending ids and letting consumers fetch via authorised API. Consider schema design (separate PII fields), logging redaction, and crypto-shredding by deleting a subject key to meet erasure requests in an immutable log.

A consumer gets TopicAuthorizationException / GroupAuthorizationException. What do you check?
Answer

The principal needs Read on the topic AND Read on the group (--group), plus Describe. Producers need Write (and IdempotentWrite on the cluster for idempotence on older versions, until 3.0 where it was relaxed, verify; Transactions need Write on TransactionalId). Check principal naming with mTLS DN mapping, kafka-acls.sh --list, and the authorizer logs (log4j.logger.kafka.authorizer.logger=DEBUG).

Worksheet

Event notification vs event-carried state transfer: when each?
Answer

Notification (thin): minimal payload with ids; consumer fetches details by API. Pros: small, always-fresh data, no schema bloat; cons: runtime coupling and load on producer's API, race conditions (data changed again). Carried state (fat): payload has the data the consumer needs; consumers build local read models; resilient to producer downtime, replayable; cons: larger payloads, schema coordination, data duplication and PII spread. Use fat events for cross-team integration and replay, thin ones for same-team triggers.

Choreography vs orchestration saga: compare using a "new hire onboarding" flow.
Answer

Choreography: HR emits EmployeeHired; IT creates accounts and emits AccountCreated; Payroll sets up pay, Facilities assigns desk; each reacts. Pros: decoupled, simple at start; cons: flow is implicit, hard to see/monitor/cycles. Orchestration: an onboarding service sends commands and tracks state (state machine persisted, timeouts, compensations like RevokeAccount). Pros: explicit, observable, easier error handling; cons: central component. Either needs idempotent handlers, correlation ids in headers, timeouts and compensation events, and a way to see saga state.

Can you use Kafka as an event store for event sourcing? Pros and cons.
Answer

Pros: durable ordered log per partition, replay, retention, scalable fan-out. Cons: no efficient "load all events for aggregate X" (must scan partition or maintain a Streams state store), no optimistic concurrency on append (no "expected version" check), topic-per-aggregate-type with key-based partitions, schema evolution over years, compaction destroys history, retention limits (use tiered/infinite). Common compromise: events in a transactional DB (append with expected-version check) as source of truth, published via outbox to Kafka for consumers.

How do you evolve an event schema without breaking consumers over years?
Answer

Additive changes only with defaults (FULL_TRANSITIVE), never repurpose fields, deprecate and remove after a sunset period, version in the event type name (SalaryChanged.v2) only for breaking semantics with dual publishing, consumers use tolerant reader (ignore unknown fields/types), contract tests in CI, and registry checks as a gate. Keep unknown-type default handlers so a new event type does not crash old consumers.

When would you NOT use Kafka?
Answer

Low-volume task queues needing per-message acks/retries/priorities/delays (RabbitMQ/SQS), request-reply RPC, small teams without ops capacity (use a managed offering or SQS), workloads needing per-message TTL/routing, tiny scale where a DB table or SQS suffices, and when strict global ordering is needed at scale (one partition limits throughput). Kafka is also awkward as a random-access store.

Kafka vs SQS FIFO for processing payroll jobs: compare.
Answer

SQS FIFO: exactly-once processing within a 5 min dedup window using MessageDeduplicationId, ordering per MessageGroupId, per-message visibility timeout/retries, DLQ with redrive, no replay, throughput limits (higher with high-throughput mode), zero ops, 14-day max retention. Kafka: replay, multiple consumer groups, higher throughput, stream processing, CDC ecosystem, ordering by key, but you build retry/DLT/dedup yourself and operate it (or pay for managed). If the pipeline is a job queue, SQS wins; if payroll events fan out to audit, analytics and exports with replay needs, Kafka wins.

Kafka vs Kinesis vs Pulsar: what differences matter in design discussions?
Answer

Kinesis: managed, shard limits (1 MB/s or 1000 rec/s in per shard, 2 MB/s out, enhanced fan-out), retention up to 365 days, simple but throttling and shard management; Kafka offers higher per-partition throughput, richer ecosystem (Connect, Streams, Schema Registry). Pulsar: separates serving brokers from storage (BookKeeper) enabling fast scaling/tiering, native multi-tenancy, geo-replication, queue and stream subscriptions; smaller ecosystem and more moving parts. Kafka's strengths: ecosystem and community, mature operations knowledge.

Design a payroll event pipeline where accuracy must be 100%.
Answer

Requirements: no lost, no duplicated, no mis-ordered pay changes; auditable; recoverable. Answer

Design audit logging with Kafka.
Answer

Services publish audit events (who, what, when, before/after hash, traceId) to audit.events (keyed by entityId, RF=3, acks=all, 30 days + tiered/long retention). Sinks via Connect: S3 sink (Parquet, partitioned by date, object lock for immutability), OpenSearch sink for search/Kibana dashboards. Protect PII (field encryption/tokenisation, hash), ACLs: write-only for services, read for audit team. Use outbox for events that must match DB commits; fire-and-forget (acks=1, async) is acceptable only for low-criticality logs. Add schema registry and tamper-evidence (hash chaining) if required.

Traffic suddenly grows 10x for an hour. What do you do, and what should have been designed in advance?
Answer

Immediate: check producer and broker saturation (request handler idle, network, disk), consumer lag per partition; scale consumers up to partition count (HPA on lag via KEDA); producers: enable compression/larger linger to improve efficiency; use quotas to protect critical topics; shed non-critical load. If partitions are the cap, adding partitions mid-incident breaks key ordering: prefer to have over-provisioned partitions upfront. Designed in advance: partition headroom (2-3x), load tests with kafka-producer-perf-test.sh, autoscaling policy on lag, back-pressure (pause/resume), priority topics, capacity for N-1 broker failure, alerts on trend. After: backlog drains; verify downstream limits; postmortem.

It is 3 AM and consumer lag is growing on payroll.export. Give your triage ladder.
Answer

1) Scope: one group/partition or all? (kafka-consumer-groups.sh --describe). 2) Is the group stable or rebalancing (--state, logs)? 3) Producer side: did incoming rate spike (batch job, replay, hourly batch)? 4) Consumer side: downstream latency/errors (provider, DB), thread dumps, GC, DLT rate. 5) Broker side: URP, ISR shrink, disk, request idle, one hot broker. 6) Recent changes: deploy, config, schema, partition change. 7) Mitigate: scale consumers (if partitions available), pause non-critical consumers, raise throughput settings, fix/disable the bad downstream, skip/DLT a poison pill. 8) Communicate and verify with reconciliation that nothing was dropped. Document for the postmortem.

How would you replay 7 days of events to rebuild a read model without disturbing production?
Answer

Create a new consumer group (or new service version writing to a new table/index), auto.offset.reset=earliest or seek by timestamp to now-7d, verify retention covers it, throttle (max.poll.records, client quota), write to a shadow store, suppress external side effects (emails, payments) via a replay flag, use idempotent upserts, monitor lag falling, then cut over (blue/green) and delete the old model. Use read_committed if transactional producers were used. If data older than retention is needed: restore from S3 archive via a sink-reversed source connector or batch loader.

Commonly used code snippets

Copy-ready commands and code for day-to-day Kafka work, each with the one trap interviewers like to probe.

1 · CLI you will actually use (topics, groups, offsets)

💡 TipOffsets can only be reset when the group is inactive. Partitions can be increased but never decreased, and increasing changes the key-to-partition mapping (per-key ordering breaks across the change). Scripts are kafka-topics.sh on Apache tarballs and kafka-topics on Confluent packages.

2 · Durable, idempotent producer (plain Java client)

💡 TipDurability is a pair: acks=all on the producer plus min.insync.replicas on the topic. The record key chooses the partition (hash), so use a stable key (orderId, accountId) for per-entity ordering. send() is async: ignoring the callback means silent data loss.

3 · Consumer poll loop with manual commit (at-least-once)

💡 TipCommitted offset = next record to read (last processed + 1). Process then commit gives at-least-once; commit then process gives at-most-once. If processing takes longer than max.poll.interval.ms the member is kicked out and the group rebalances: lower max.poll.records or hand work to another thread and pause/resume.

4 · Spring for Apache Kafka: config, template and listener

💡 TipSpring Kafka 3.0+ returns CompletableFuture from send() (it was ListenableFuture in 2.x). Set spring.json.trusted.packages deliberately: * lets a producer pick any class to deserialize. For schema-evolving payloads prefer Avro/Protobuf with Schema Registry over raw JSON type headers.

5 · Error handling: retries, backoff and dead-letter topic

💡 TipBlocking retry (DefaultErrorHandler) pauses the partition and preserves order; @RetryableTopic unblocks the partition but breaks ordering for retried records. A DLT nobody monitors is just a slower data-loss path: alert on its depth and keep the original topic, partition, offset and exception in headers.

6 · Idempotent consumer and transactional consume-transform-produce

💡 TipExactly-once holds inside Kafka only. As soon as you write to a database, call an HTTP API or send an email, you need an idempotent side effect or the outbox pattern (write the event in the same DB transaction, publish it with a relay or Debezium). Say "effectively-once", never "end-to-end exactly-once".

7 · Transactional outbox and Debezium connector

💡 TipThe outbox gives at-least-once publishing with correct ordering per aggregate, so consumers must still be idempotent. Keep secrets out of connector JSON by using a config provider (${file:...}). Delete or archive processed outbox rows or the table grows forever.

8 · Kafka Streams: stateless and stateful basics

💡 TipStateless ops (map, filter) are cheap; anything that changes the key or aggregates may create repartition and changelog topics. Input topics of a join must be co-partitioned (same partition count and partitioner). Use exactly_once_v2 (needs brokers 2.5+).

9 · Testing: EmbeddedKafka and Testcontainers

💡 TipPrefer Testcontainers when behaviour depends on real broker semantics (transactions, rebalances, compaction). Assert with Awaitility, not sleeps, and give each test its own topic or group id so tests cannot see records from other tests.

10 · Topic config recipes (compaction, retention) and quick diagnostics

💡 TipRetention deletes whole closed segments, so an old record may outlive retention.ms until its segment rolls. Compaction never touches the active segment and keeps the latest value per key; tombstones are retained for delete.retention.ms so slow consumers can see the delete.
